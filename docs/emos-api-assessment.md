# EMOS 音乐客户端 API 问题与接口建议

## 当前 API 范围

EMOS 音乐客户端当前可稳定使用的接口集中在歌曲、专辑、人物、歌词、媒体资源、收藏和登录态校验几类能力：

- `GET /music/song/list`：歌曲列表、歌曲详情、歌手热门歌曲、专辑歌曲、收藏歌曲。
- `GET /music/song/search`：歌曲搜索。
- `GET /music/album/list`：专辑列表、专辑详情、歌手专辑。
- `GET /music/person/list`：歌手列表与歌手详情。
- `GET /music/song/{id}/lyric/list`：歌词与制作信息解析。
- `GET /music/song/{id}/media/list`：获取可播放媒体资源列表。
- `GET /music/song/{id}/media/playUrl`：获取实际播放地址。
- `GET /sign/check`：校验已有登录态，只返回登录状态与用户标识，不签发 token，也不返回 token。
- `PUT /music/favorite`：歌曲、专辑、歌手收藏，`type` 分别使用 `ms`、`ma`、`mp`。

登录 token 的来源是 link 登录回跳。`/sign/check` 的职责是校验登录态，这个职责边界是合理的，不应被视为 API 缺陷。

## API 问题

### 歌曲列表与搜索字段不一致

`/music/song/list` 与 `/music/song/search` 的歌曲结构不完全一致。搜索结果常缺少 `duration`、`albums`、封面图、媒体可用性等列表渲染和播放判断所需字段，导致同一首歌在“列表返回”和“搜索返回”两种场景下需要按不同结构理解。

建议将歌曲摘要结构标准化。无论来自列表、搜索、专辑歌曲还是歌手歌曲，至少应稳定返回 `song_id`、`name`、`duration`、`album`、`person_artists`、`image_poster_url`、`has_media`、`count_medias`、`is_favorite`。如果某些字段无法计算，应返回 `null` 或空数组，而不是在不同接口中省略字段。

### 歌手标识不可稳定关联

歌曲列表和搜索结果中的 `person_artists[].person_id` 经常为 `null`，但 `/music/person/list` 中的 `person_id` 又是可用的。这会让歌曲与人物实体之间缺少稳定外键，影响歌手详情、歌手聚合、同艺人作品等能力。

建议在歌曲相关响应中补齐 `person_artists[].person_id`。如果历史数据无法直接关联，应提供按名称精确匹配人物实体的接口，例如 `/music/person/resolve?name=...`，返回匹配置信度、候选人物和唯一命中结果，避免调用方自行猜测。

### 可播放状态字段语义不一致

`has_media` 与 `count_medias` 偶尔不一致。一个字段表达“是否存在可播放资源”，另一个字段表达“媒体资源数量”，两者如果同时存在，应具备明确一致的语义关系，否则会影响歌曲是否可播放、是否展示、是否允许加入播放队列等判断。

建议明确媒体状态字段的定义。`has_media` 应表示当前歌曲至少存在一个可播放资源；`count_medias` 应表示资源总数；如果资源存在但不可播放，应另设 `media_status` 或 `playable` 字段区分“无资源”“有资源但不可用”“可播放”。媒体资源列表也应返回不可用原因，例如资源失效、权限不足、转码中或源文件缺失。

### 播放地址缺少生命周期信息

`/music/song/{id}/media/playUrl` 返回实际播放地址，但缺少有效期、资源状态和失败原因等信息。播放地址通常可能受签名、代理、缓存或存储策略影响，没有生命周期字段会让调用方难以判断何时应重新获取播放地址。

建议播放地址响应增加 `expires_at`、`ttl_seconds`、`mime_type`、`bitrate`、`size`、`media_id`、`playable`、`reason` 等字段，让播放地址具备可缓存、可诊断、可重试的基础信息。

### 收藏能力缺少独立查询接口

`PUT /music/favorite` 可以切换歌曲、专辑、歌手收藏状态，但缺少独立的收藏分页查询接口。收藏是用户资料库的核心数据，单靠通用列表参数推断收藏集合，会让分页、排序、总数统计和收藏时间展示都不稳定。

建议增加统一收藏查询接口，例如 `/music/favorite/list?type=ms|ma|mp&page=1&page_size=50`。响应应包含 `items`、`total`、`page`、`page_size`、`favorite_time`、`resource` 等字段，并让资源结构与对应实体接口保持一致。

### 歌单实体缺失

当前 API 具备专辑能力，但缺少独立歌单实体。专辑和歌单的业务语义不同：专辑通常来自发行作品，歌单则需要创建者、描述、标签、歌曲排序、收藏状态、更新时间、公开状态等字段。

建议增加歌单实体接口，至少包括歌单列表、歌单详情、歌单歌曲分页、歌单收藏状态、创建者信息、描述、标签和歌曲顺序。歌单歌曲项还应保留加入时间、排序位置和歌曲摘要，避免把歌单退化成普通歌曲集合。

### 搜索能力需要聚合结果

当前搜索以歌曲搜索为主，缺少统一多类型搜索。音乐客户端的搜索通常需要同时返回歌曲、专辑、歌手和歌单等结果，并提供各类型总数，便于后续分页加载某一类结果。

建议提供统一搜索接口，例如 `/music/search?keyword=...&types=ms,ma,mp,playlist`。响应可按类型分组返回 `songs`、`albums`、`persons`、`playlists`，每组包含 `items`、`total`、`has_more`，并保证每类资源结构与各自列表接口一致。

### 歌词与制作人员没有结构化

`/music/song/{id}/lyric/list` 能提供歌词文本，但制作人员、翻译歌词、逐字歌词等信息缺少稳定结构。把制作人员混在歌词文本中会让角色、人员、语言和时间轴都难以可靠解析。

建议将歌词和制作人员拆成结构化字段。歌词部分可提供 `lrc`、`translated_lrc`、`word_timeline`；制作人员部分可提供 `credits: [{ role, persons: [{ person_id, name }] }]`。如果暂时无法完整结构化，也应至少提供原始来源字段和解析状态，方便判断数据可信度。

## 接口设计建议

### 统一实体摘要

歌曲、专辑、人物、歌单都应有稳定的摘要结构，用于列表、搜索、收藏和关联结果。摘要结构不需要包含详情页所有字段，但必须包含可展示、可跳转、可分页和可判断状态的核心字段。

建议为每类实体定义固定字段集合。歌曲摘要包含 ID、名称、时长、封面、专辑、艺人、媒体状态和收藏状态；专辑摘要包含 ID、名称、封面、艺人、发行时间、歌曲数和收藏状态；人物摘要包含 ID、名称、头像、简介摘要和收藏状态；歌单摘要包含 ID、名称、封面、创建者、歌曲数、更新时间和收藏状态。

### 保持分页协议一致

当前分页结构以 `page`、`page_size`、`total`、`items` 为主，这个方向是合理的。后续新增接口应继续沿用同一分页协议，避免不同资源使用不同分页字段。

建议所有列表接口都返回 `page`、`page_size`、`total`、`items`，并明确排序规则。若接口支持游标分页，应另设 `cursor` 和 `next_cursor`，不要与页码分页混用。

### 明确状态字段语义

状态类字段需要避免重复表达同一含义。`has_media`、`count_medias`、`playable`、`media_status` 如果同时存在，应分别表达不同层级：是否有关联资源、资源数量、当前是否可播放、不可播放原因。

建议用枚举表达复杂状态。例如 `media_status` 可取 `none`、`processing`、`available`、`unavailable`，并用 `media_status_reason` 解释原因。这样比多个布尔字段更容易保持一致。

### 登录态接口保持单一职责

`/sign/check` 只校验登录态是合理设计。它不需要承担 token 签发、刷新或恢复职责，否则会混淆登录入口、凭证签发和状态校验三个不同阶段。

建议保持 `/sign/check` 的职责边界，只返回登录是否有效、用户标识、必要的账号状态。如果未来需要 token 刷新，应设计独立的刷新接口，并明确刷新凭证、过期时间和安全约束。
